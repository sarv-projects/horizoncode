# 02 — Requirements

Observable, falsifiable requirements. Grouped by area. `MUST` = hard requirement; `SHOULD` = strong default with a documented escape.

## VISION / packaging

- `REQ-VISION-001` — HorizonCode MUST ship one primary executable per supported target where feasible. Required and optional host capabilities (for example sandbox helpers, Git, language servers, local inference servers, or a supervised detached controller) MUST be probed, disclosed, version-checked where needed, and refused with actionable guidance when an effect cannot meet its declared contract. “Single executable” MUST NOT imply that every capability has no host dependency (`DEC-030`).
- `REQ-VISION-002` — The installer/updater MUST detect and report the host toolchain prerequisites it needs (e.g. absent build tools) with actionable instructions, and MUST NOT silently fail.
- `REQ-VISION-003` — Product positioning and help MUST remain neutral and evidence-bound. Factual provider/model names required for configuration, route selection, usage, attribution, and source provenance MAY appear; no peer name may imply an unmeasured quality claim (`DEC-030`).
- `REQ-VISION-004` — The runtime MUST be deployable on a user-selected laptop/workstation or user-managed server. Headless server use MUST NOT require a HorizonCode-operated service or an interactive TUI. Run state, controller, and workspaces MUST remain under the configured host's custody; the selected inference route and its data transfer MUST be shown and governed separately. A server deployment MUST NOT imply remote UI attachment or remote-control support unless a distinct authenticated protocol is implemented and accepted (`DEC-046`).
- `REQ-VISION-005` — Fast prompt-led coding MUST be a first-class workflow alongside managed long-horizon Runs. An ordinary turn MUST be able to explain or locate code, debug, make a focused change, run a relevant check, inspect a diff, and accept a correction without first creating a goal, preparing a plan, or accepting a Run review. The user MAY choose a managed Run when requested or warranted; help and product claims MUST describe both paths (`DEC-075`).

## UPDATES AND DISTRIBUTION

- `REQ-UPDATE-001` — When enabled, the interactive TUI MUST check signed update metadata for the locally selected channel at startup without blocking or delaying session startup. Non-interactive CLI/headless invocations MUST NOT perform an unsolicited update check; the user can request one with `hzcode upgrade --check`. The default channel is `stable`; `preview` is checked only after an explicit user choice and only while signed preview targets are published. Checks MUST be rate-limited, bounded by a timeout, cancellable, and use cached verified metadata when offline. Finding an update MUST only notify; installation MUST require an explicit operator action.
- `REQ-UPDATE-002` — The TUI MUST present a non-blocking, accessible update notice with version, channel, concise release notes, and `Install`, `Later`, and `Details` actions. `hzcode upgrade` MUST offer an equivalent interactive review/confirmation; `hzcode upgrade --check` MUST be read-only. `/upgrade` MUST call the same update service and confirmation policy. Non-interactive and structured-output calls MUST not receive unsolicited stdout output. The installed `horizoncode` compatibility alias MUST have identical behavior and state to `hzcode`.
- `REQ-UPDATE-003` — Every install and update path MUST authenticate metadata and target artifacts against a locally trusted, rotatable signing root; enforce target OS/architecture/channel, bounded size/hash, expiry, monotonic version/rollback rules, and compatibility metadata before staging. TLS and an artifact checksum served from the same unauthenticated origin are not sufficient trust. The chosen update framework, library, license, bootstrap trust, and key lifecycle MUST be recorded before implementation (`ARCH/30`, `ARCH/05`).
- `REQ-UPDATE-004` — Updates MUST download to a bounded staging location, verify before execute, preserve the installed executable until an atomic activation point, and retain a known-good rollback target until startup health checks pass. Interrupted download, corrupt metadata/archive, disk exhaustion, permission failure, unsupported platform, migration incompatibility, or failed new-version startup MUST leave the old executable and user state recoverable.
- `REQ-UPDATE-005` — Updates MUST NOT kill, migrate underneath, or change the executable used by an active run. They MUST stage and defer application until a safe process restart boundary with no active worker execution, or until the controller has durably paused/reconciled all work and the operator explicitly confirms the maintenance transition. Before activation, the run controller MUST atomically close admission to new runs/attempts, confirm there is no active or unknown execution/effect, and hold a maintenance fence through replacement, health check, and rollback/commit. If the controller is unavailable or cannot prove quiescence, activation MUST defer. Existing runs keep their pinned model, provider adapter, context, spec, and policy snapshots.
- `REQ-UPDATE-006` — `/settings updates` MUST expose check-on-start, notifications, stable/preview channel when published, last checked/current version, and managed source/lock state. Disabling checks MUST not disable manual `hzcode upgrade --check`; muting notifications MUST not suppress explicit command results. A CLI `--channel` is a one-command override and MUST NOT mutate the persistent setting; only an explicit settings change does that. Project instructions, provider metadata, or model output MUST NOT alter updater roots, source, channel, or installation consent.
- `REQ-UPDATE-007` — Installation MUST identify its management method and supported target. The canonical package/install name MUST be `hzcode`; installed `hzcode` and `horizoncode` commands MUST invoke the same binary and state. A package-manager-owned install MUST be upgraded by that manager, not overwritten by the self-updater. The standalone installer and every supported OS/package channel MUST bootstrap a trusted update root, verify platform compatibility and permissions, and provide a non-destructive uninstall/repair path. Convenience scripts MUST be thin, auditable launchers, never `curl | sh`, ad-hoc signature implementations, or a bypass around the signed installer.

## LOOP

- `REQ-LOOP-001` — The agent MUST run a bounded step loop driven by model decisions, with a configurable maximum step count per turn.
- `REQ-LOOP-002` — The loop MUST accept **steer** (interrupt-level redirection) and **queue** (next-turn) inputs while a turn is running, without losing either.
- `REQ-LOOP-003` — Tool calls within a turn MUST execute concurrently when independent and MUST honor explicit ordering barriers when declared.
- `REQ-LOOP-004` — Every turn MUST terminate in exactly one terminal state: completed, failed, interrupted, or declined.
- `REQ-LOOP-005` — Interruption MUST stop in-flight model streaming promptly and MUST leave partial work inspectable, not silently discarded.
- `REQ-LOOP-006` — The loop MUST persist events incrementally so a crash mid-turn loses no committed step.
- `REQ-LOOP-007` — Steer, queued prompt, and clarification inputs MUST have stable caller-supplied or generated delivery IDs, durable admission receipts, bounded payload/count/age limits, and idempotent retry semantics. A duplicate ID with the same digest returns the original receipt; the same ID with different content is a typed conflict. Compaction MUST NOT erase admitted-but-unconsumed input.
- `REQ-LOOP-008` — Every model response MUST be fully assembled and admitted as one bounded tool-call batch before any call from that response executes. The controller MUST cap call count, aggregate serialized argument bytes, and retained response bytes per response as well as per turn/run. Exceeding any cap MUST cancel collection and reject the entire unstarted batch with a typed durable outcome, and dispatch none of its calls. No adapter may partially dispatch a response batch. Reported generation usage is still charged; call-count limits do not cap model generation tokens. A rejected batch MUST not be retried unchanged without a recorded strategy change.
- `REQ-LOOP-009` — HorizonCode-managed turns MUST use locally settled tools behind the HorizonCode guard, confinement, and audit path. Provider-hosted execution tools or remote tool execution MUST remain unavailable unless a separately approved contract defines authorization, effect receipts/reconciliation, cancellation, egress, and the limits of local security claims. An unsupported remote call MUST be refused before dispatch/settlement and MUST NOT count as success.
- `REQ-LOOP-010` — An ordinary direct turn MUST have a finite, visible per-turn ceiling for tool calls/steps, elapsed time, model output, and any provider-reported spend that can be enforced. The user MUST be able to continue or raise a ceiling explicitly. Unknown provider billing MUST remain unknown; it MUST NOT be represented as a monetary cap. Defaults MUST be chosen from the paired quick-task evaluation, not fixed without evidence (`DEC-075`).
- `REQ-LOOP-011` — Escape/Ctrl-C in an ordinary turn MUST request provider cancellation, cancel in-flight tool work where possible, and fence late results from mutating files after cancellation. Spawned command trees MUST be supervised with a bounded graceful-stop period and forced termination where the platform supports it. A child/effect that remains unknown MUST be shown as cancellation-pending and MUST block conflicting new work until reconciled; interruption MUST NOT be described as instantaneous or as rollback (`ARCH/08`, `ARCH/13`, `ARCH/22`).
- `REQ-LOOP-012` — After a meaningful edit, the runner SHOULD choose a relevant bounded project check when one is known and authorized. Failures MAY be returned as evidence for a bounded repair attempt. It MUST distinguish not-run, passed, failed, cancelled, and unknown; it MUST not run a full suite after every individual write by default or convert model claims into check evidence (`ARCH/08`, `DEC-032`).

## TOOLS

- `REQ-TOOL-001` — The agent MUST provide first-party native tools for read, write, edit, apply-patch, glob, grep, shell, todo, question, webfetch, and websearch.
- `REQ-TOOL-002` — Every tool MUST declare a typed input schema, a typed output schema, and an optional structured result.
- `REQ-TOOL-003` — Tool registration MUST be permission-filtered: a tool denied by policy MUST be absent from the model's tool set, not merely blocked at call time.
- `REQ-TOOL-004` — Tool results MUST separate model-visible content from UI-only detail.
- `REQ-TOOL-005` — Tool names MUST match `^[A-Za-z][A-Za-z0-9_-]{0,63}$`.
- `REQ-TOOL-006` — A question/elicitation request in a provider response is a control boundary. Before dispatching any sibling tool call, the controller MUST detect and validate the complete bounded response. If one valid question call shares a batch with other calls, it MUST suspend the batch, dispatch no sibling (including read-only) effects, deliver only the validated question, and resume with a typed `not_run_question_boundary` result for suppressed siblings after the answer so the model can replan. An invalid/malformed question, multiple question calls in one batch, or malformed response MUST reject the whole unstarted batch and dispatch zero calls. Tool execution already started before a separately delivered external elicitation is received MUST be cancelled where possible and reconciled; no rollback is implied. (`ARCH/10`, `ARCH/25`, `ARCH/23`.)
- `REQ-TOOL-007` — After compaction has removed older visible turns from the current prompt, an explicitly enabled `history_search`/`history_read` tool MAY retrieve prior committed, user-visible records from the current HorizonCode Thread through the planned shared `CMP-session` canonical history/search API. Thread identity is supplied by the controller, never by model arguments; each result is bounded, cites immutable event/message IDs and source sequence, reports incomplete/expired/unavailable status, and remains untrusted context rather than verifier evidence. Hidden reasoning, ephemeral deltas, uncommitted content, and tool output not enabled for display/search MUST be excluded. This reuses the planned owner/index and MUST NOT introduce a second archive, database, or permission path. (`ARCH/07`, `ARCH/10`, `ARCH/23`.)
- `REQ-TOOL-008` — `exec.run` MUST support user-configured shell profiles for supported command interpreters, including PowerShell and Bash and extensible to other installed shells. The effective executable, argv template, working directory, environment, platform, and pipe/PTY mode MUST be visible and governed through the existing Guard/Sandbox/Audit path. Command text MUST be passed without constructing an intermediate shell string; profile selection MUST NOT change confinement or permission semantics (`DEC-077`).
- `REQ-TOOL-009` — Non-interactive commands MUST use bounded pipe-based capture by default. A PTY MAY be used for an explicitly interactive command/profile and MUST support bounded streaming, resize, cancellation, and truthful full-output recall. PTY allocation MUST NOT be treated as a sandbox or authority boundary. The controller MUST cap concurrent process/descriptor or handle consumption and reserve capacity for operator control and cleanup (`ARCH/10`, `ARCH/13`, `ARCH/16`).

## CTX (context)

- `REQ-CTX-001` — The context engine MUST maintain a ranked repository map derived from tracked files and language parsing.
- `REQ-CTX-002` — Automatic compaction MUST be enabled by default and trigger before dispatch when the estimated assembled context reaches the configured fraction of the active route's resolved model context window (`compaction.auto_threshold`, default `0.5`). The fraction MUST be evaluated against the selected model/route window, not a fixed token count. Compaction MUST preserve a serialized recent tail plus a structured summary. Before either automatic or explicit manual compaction dispatches its summary request, the engine MUST verify that the bounded summary input plus output allowance fits the selected compaction model's resolved context window; if it cannot fit, return a visible typed compaction-fit error without silently skipping, switching models/routes, or dispatching the original over-budget request. The output/buffer/estimation-uncertainty reserve remains a separate hard fit guard. When `compaction.auto=false`, every automatic compaction path is disabled (threshold and all recovery triggers), but explicit manual compaction remains available. The hard fit guard remains active and MUST refuse an oversized request with typed `CONTEXT_TOO_LARGE` guidance; it MUST NOT dispatch an over-budget request or silently compact (`ARCH/09`, `DEC-006`).
- `REQ-CTX-003` — Compaction quality MUST be gated by a retrieval evaluation, not only by fitting the window.
- `REQ-CTX-004` — The engine MUST estimate the fully assembled request before each model dispatch and enforce the route's hard usable-context bound. If a provider rejects a request for context-window overflow before any response content, tool call, or provider-side effect is exposed, the controller MAY perform exactly one automatic compaction and retry of the same logical step only when `compaction.auto=true`, the user/control/task/workspace/spec/policy revisions and pinned route are unchanged, and compaction, retry, and required verification fit the reserved budget. If `compaction.auto=false`, return typed `CONTEXT_TOO_LARGE` guidance without automatic compaction or retry. A second rejection is terminal; unknown provider errors, output-cap truncation, or any possible effect are not this recovery class (`ARCH/08`, `ARCH/09`, `ARCH/11`, `DEC-054`).
- `REQ-CTX-005` — Project instructions (`AGENTS.md`) MUST be discovered hierarchically (user → repository walk) and injected as a typed context source.
- `REQ-CTX-006` — The engine MUST reduce tool observations with native, deterministic per-command formatters (filter/group/truncate/dedupe) plus a full-output recall store; formatters MUST be eval-gated per command family and MUST NOT depend on an external filter binary.
- `REQ-CTX-007` — The engine MUST produce a deterministic, versioned context projection and let each provider adapter render it in that API's required order and cache-control format. Where supported, static-prefix/cache breakpoints MUST be explicit and immutable within a context epoch; cache-read/creation/input usage MUST be recorded as separate provider-reported fields and MUST NOT be assumed when unsupported. Replacing the complete effective system prompt is the safe default. An adapter MAY append a system-prompt update inside history only when a pinned provider/model capability documents that later-message semantics and route conformance verifies the exact effective prompt; cache support or OpenAI compatibility alone MUST NOT imply it.
- `REQ-CTX-008` — Code and tool observations MUST be compressed by verbatim selection/grouping only; abstractive summarization is permitted for prose only and MUST follow a structured schema (decisions / open bugs with exact errors / file refs / next step / discarded-and-where-to-recover).
- `REQ-CTX-009` — Every compression change MUST be gated by a paired per-task evaluation with a pre-registered sample size and endpoints; three pairs are smoke evidence only. Report task success, raw per-task outcomes, cost/turn, latency, recall, and uncertainty. Output-byte reduction or compressor-internal counters MUST NOT be presented as cost savings or task evidence.
- `REQ-CTX-010` — Extension tool catalogs MUST be discoverable without injecting every tool schema into each model request. The selected schema set MUST be permission-filtered, token-budgeted, version-pinned for a model step, and refreshable at a new context epoch; unavailable or changed tools MUST fail typed before execution. Tool names, descriptions, schemas, examples, and catalog metadata are untrusted data: bound their rendered bytes/tokens, escape framing/control delimiters, preserve provenance, and mark them as data before they enter a model or reviewer context. Oversized descriptions are omitted whole with an explicit non-authorizing omission marker; they are never silently truncated into instruction-like text.
- `REQ-CTX-011` — Provider termination MUST preserve a typed finish reason that distinguishes normal completion, pre-content context-window rejection, explicit output-token-cap truncation, proven remaining-context output truncation, and unknown truncation. A route with explicit evidence that generation stopped at the remaining-context output cap MAY trigger exactly one automatic compaction and retry of the same logical step only when `compaction.auto=true`, no tool was dispatched and no provider-side tool/effect was enabled or could have executed, all user-input/control/task/workspace/spec/policy revisions and the pinned route are unchanged, and compaction plus retry plus required verification fit the reserved budget. With `compaction.auto=false`, no automatic recovery occurs. Partial bytes, usage, and the failed attempt MUST remain inspectable and MUST NOT be treated as a complete assistant message; an explicit output cap, unknown cause, repeated truncation, changed input/control state, or any possible side effect MUST NOT auto-retry. This response-truncation class is distinct from the pre-content provider rejection in `REQ-CTX-004` (`ARCH/08`, `ARCH/11`, `DEC-054`).
- `REQ-CTX-012` — Repository intelligence MUST combine a cheap deterministic file/manifest map with revision-bound symbol/navigation evidence when parser, LSP, or SCIP sources are available. Indexing MUST be lazy/incremental, cancellable, bounded, and non-blocking. Results MUST identify repository revision and freshness; stale or unavailable semantic data MUST fall back to explicitly labeled text search or direct reads rather than appear authoritative.
- `REQ-CTX-013` — Direct Thread compaction MUST support a lightweight rebuildable narrative summary plus a recent verbatim tail without requiring managed Run/task-graph headings. It MUST preserve the active user request, subsequent corrections, decisions, relevant evidence/error/path references, and unresolved questions. The canonical Thread event history, not the summary, remains truth; summary evaluation MUST measure lost and resurrected instructions as well as task success (`DEC-075`).
- `REQ-CTX-014` — Repository retrieval MAY combine lexical/BM25 search, syntax/symbol/reference ranking, and local vector retrieval. Semantic indexing MUST be off by default, cancellable and bounded, disclose storage and any egress before use, and work in local-only mode. Every result identifies source, revision/freshness, and retrieval mode; unavailable/stale semantic results fall back to lexical search. Search quality and overhead MUST be evaluated against natural-language and exact-token queries before enabling by default.

## PROV (providers)

- `REQ-PROV-001` — The agent MUST support hosted and user-configured compatible HTTP endpoints, including local inference servers. A provider being listed or API-compatible MUST NOT imply concrete model/template capability (`REQ-PROV-006`).
- `REQ-PROV-002` — The built-in primary catalog MUST be usable offline and carry per-record provenance. The OpenCode-backed provider/model registry is a separately identified, automatically refreshable source, enabled by default and disableable in settings; it MUST be cached, schema-validated, content-hashed, provenance-stamped, and unable to grant credentials, invent auth mechanisms, load executable adapters, or select arbitrary network origins. Its data is advisory and its transport/auth implementation remains HorizonCode-owned Rust code (`DEC-021`, `DEC-060`).
- `REQ-PROV-003` — Provisional model quirk handling (thinking passthrough, reasoning fields, streaming framing) MUST be isolated per provider.
- `REQ-PROV-004` — Credential values resolved from `CMP-secrets` MUST never be written to logs, model prompts, telemetry, events, or the audit log. Provider diagnostics and receipts MUST use typed allowlisted fields, configured/broker-known value redaction, and bounded recognized-pattern redaction before persistence or display; redaction is a property of the typed producer/persistence/display path, not a special debug-view filter. Redaction canaries MUST cover logs, durable events, UI/control notifications, exports, and provider/config inspection surfaces. Arbitrary repository, tool, or provider text is untrusted content and MUST NOT be presented as perfectly secret-scanned; it requires an explicit bounded artifact/access path or rejection. (`ARCH/11`, `ARCH/14`, `ARCH/18`, `ARCH/22`.)
- `REQ-PROV-005` — Routing MUST be configurable by policy and MAY be eval-gated; routing decisions MUST be observable.
- `REQ-PROV-008` — A run MUST pin an immutable provider route snapshot containing provider/model IDs, endpoint origin and path, protocol adapter/version, auth method ID (never secret material), model capability/limit/pricing provenance, resolved system-prompt update mode, catalog digest, and selected model metadata digest. Refresh changes future selection only; it MUST NOT rewrite an active attempt or prior cost/verification facts. An explicit replan creates a new context/route epoch and is subject to controller policy.
- `REQ-PROV-009` — The native Rust OpenCode Go adapter MUST read the separately documented Go model directory at `https://opencode.ai/zen/go/v1/models` and use only the user's own OpenCode Go API key from `CMP-secrets` for authorized inference after an eligible subscription. It MUST identify itself with HorizonCode's own product User-Agent and send a stable opaque HorizonCode conversation ID as `x-opencode-session`. It MUST NOT send the Go credential to `https://models.opencode.ai/api.json`, impersonate OpenCode, reuse OpenCode OAuth client IDs/auth files/cookies/cached tokens, or infer an undocumented auth flow. Inference is restricted to the fixed Go service origin `https://opencode.ai/zen/go/v1` and the locally allowlisted `/responses`, `/chat/completions`, and `/messages` protocol paths. Remote model IDs cannot choose an endpoint or protocol; a model without a reviewed local model-to-route mapping is visible but unavailable. Passing HorizonCode's own conformance test MUST NOT be reported as OpenCode-validated unless OpenCode's current official validated-client list names HorizonCode (`DEC-060`).
- `REQ-PROV-010` — The OpenCode provider inventory MUST be complete for each pinned inventory snapshot: enumerate every dynamic provider ID in the OpenCode model-feed response and separately enumerate every documented provider auth method, including API-key, cloud identity, OAuth/device sign-in, product subscription, local, and custom endpoint methods. The feed's `env`, `npm`, `api`, and other metadata fields are discovery hints only and MUST NOT establish an auth method or enable an adapter. For each provider/method, record catalog presence, source/revision, protocol family, adapter status, capability evidence, terms/registration review, service prerequisites, and availability. “Listed”, “sign-in option exists”, “supported”, “usable”, and “conformance tested” are distinct. Unsupported, conflicting, terms-restricted, unavailable, unknown, and awaiting registered HorizonCode OAuth client states remain visible and unusable. Only provider-documented, user-authorized flows with HorizonCode's own valid client registration may become usable.
- `REQ-PROV-011` — Provider metadata refresh MUST be background, bounded, rate-limited, atomic, and safe under concurrent processes. A failed refresh MUST retain the last valid cache and offline primary with explicit freshness/error provenance. Each source has a maximum schema/body size and parser fuzz corpus; unknown protocol/auth tags are preserved only as inert diagnostics and cannot be activated.
- `REQ-PROV-012` — A managed attempt MUST persist its selected route and any permitted ordered fallback chain before dispatch. A metadata refresh MUST NOT alter either. Cross-provider fallback is permitted only for a typed transient failure before provider content or a tool-call delta is exposed, and only to a pinned entry that independently satisfies required capabilities, policy/egress checks, and an atomic budget reservation. It MUST NOT occur for auth, authorization, quota, policy/egress, protocol/schema, capability, cancellation, or post-exposure failures. Every actual provider/model dispatch MUST have an immutable route snapshot and distinct usage evidence. See `DEC-070`, `ARCH/11`, and `ARCH/23`.
- `REQ-PROV-013` — Model capability metadata MUST distinguish `supported`, `unsupported`, and `unknown`. Missing, malformed, or unverified capability fields MUST remain `unknown`; they MUST NOT become positive capabilities through permissive defaults. A route with unknown tool, vision, structured-output, reasoning, or cache capability MUST NOT satisfy a task's requirement for that capability or cause the corresponding request feature to be enabled implicitly. Explicitly selected routes may be used only with the unknown capability surfaced and a conservative request profile. (`ARCH/11`, `ARCH/23`.)
- `REQ-PROV-014` — Provider quota observation MUST be an optional, read-only per-provider capability using only documented, user-authorized endpoints and existing credentials. Background refresh MUST be off by default; only user/managed settings, never project instructions or project config, can enable it. Explicit refresh MUST be available where supported. Enabled refresh is bounded, coalesced per provider/account, cancellable, rate-limit aware, and retains the last good observation with explicit freshness/state on failure. An observation MUST identify provider/account reference, each window and unit, reported values, retrieval time, reported window start/reset times, source, and confidence; unsupported, denied, stale, rate-limited, transient-error, and unknown states remain distinct. It MUST NOT read or rewrite another application's credential store or refresh tokens outside `CMP-secrets`; provider observations MUST NOT affect route selection/dispatch, release, increase, or replace HorizonCode's atomic local budget reservations. They may drive a clearly labeled warning only. Users MUST be able to clear local observations without revoking provider credentials or affecting remote account state. Persist bounded observations in one provider-owned store; analytics/UI are projections. (`ARCH/11`, `ARCH/20`, `ARCH/27`, `ARCH/23`.)
- `REQ-PROV-015` — Provider retries MUST have controller-owned finite attempt and elapsed-time ceilings, a maximum backoff multiplier and absolute delay, and bounded jitter. A server `Retry-After` value is parsed and clamped to those ceilings; it cannot extend the run deadline. Exhaustion MUST preserve the real terminal typed error and request/attempt identity. A retry that can replay a request body or cause provider-side work/billing is allowed only when the failure proves the request was not accepted or the provider documents an idempotency mechanism and HorizonCode supplies its stable per-effect/request key; absent that evidence/key means no replay. No feature flag, environment variable, build profile, or setting may remove these bounds (`ARCH/08`, `ARCH/11`, `REQ-SEC-013`).
- `REQ-PROV-016` — HorizonCode MUST target usable integration parity for every documented provider connector/auth path in the monitored OpenCode and Cline snapshots. A connector counts as supported only with a HorizonCode-owned, authorized credential path and route-conformance evidence; any blocker means provider parity is incomplete and MUST remain visible. HorizonCode MUST NOT impersonate another client or bypass registration/terms. An upstream monitor MUST detect relevant changes and prepare a reviewable native update candidate with per-file license/notice review and route-conformance fixtures. Runtime metadata MUST NOT install, load, or execute upstream code; a candidate affects users only through HorizonCode's reviewed, signed release and never rewrites an active route (`DEC-076`, `ARCH/05`, `ARCH/11`, `ARCH/30`).

## GUARD / AUDIT

- `REQ-GUARD-001` — Permissions MUST be expressed as ordered rules producing allow / ask / deny, evaluated deterministically.
- `REQ-GUARD-002` — The default posture MUST fail closed: an unmatched action evaluates to ask or deny per configuration, never implicit allow.
- `REQ-GUARD-003` — "Always allow" decisions MUST persist the exact pattern they remember, shown to the user before confirmation.
- `REQ-GUARD-004` — Sandboxed execution MUST default to workspace-scoped writes and a request for no outbound network unless explicitly granted. Every supported tier MUST declare one of `enforced | capability | best_effort | none` with its mechanism, proof, and residual. These labels describe tested network reachability boundaries; they do not assert that a particular syscall is blocked. `capability` means denial by absence of an OS network capability, with a separate acceptance test. The level MUST be surfaced wherever a network-restricted profile is presented and recorded in that tier's acceptance record. A caller requiring a stronger level MUST be refused, never silently degraded. A tier MUST NOT claim a level stronger than it proves (`DEC-026`, `DEC-027`).
- `REQ-GUARD-005` — A user-selectable auto-approval / “bypass approvals” posture MAY auto-approve only eligible `ask` decisions within the active run's already-approved authority ceiling. It MUST NOT override `deny`, catastrophic-effect gates, sandbox limits, managed locks, external-effect approvals, or an unavailable required enforcement backend. Enabling it requires a local, explicit, auditable confirmation bound to a run and expiry; project instructions/configuration cannot enable it. The active reduced-approval posture and remaining scope MUST remain visible in every effect-capable surface (`ARCH/12`, `ARCH/22`, `DEC-073`).
- `REQ-GUARD-006` — Every interactive effect approval MUST be a durable, expiring challenge bound to the authenticated `control_session_id`, exact `connection_ref`, principal/scope, request and displayed-content digests, effect/action/resource digests, current Thread/Run/Task/Attempt/Turn revisions, workspace/repository revisions, policy revision, and cancellation generation that were reviewed. The same authenticated connection must answer; a foreign answer is `WrongPrincipal`, connection close durably invalidates unanswered challenges before teardown, and expiry/cancel denies. After approval and after every extension/reviewer callback, the controller MUST re-read current revisions and cancellation state before minting/using a ticket. Immediately before the effect, the executor MUST re-check the approved resource/content digest and relevant revisions; any mismatch returns `STALE_APPROVAL` and requires a fresh challenge, never a silent re-ask or automatic grant. Tickets bind this challenge digest and cannot substitute for a current-world check (`ARCH/12`, `ARCH/25`, `ARCH/31`).
- `REQ-GUARD-007` — The default local interactive profile MUST support routine workspace reads/edits and configured project checks without repeated per-call confirmation when the action is inside the admitted workspace and required confinement is available. Effective policy, prompt reason, exact action/resource, grant scope/expiry, and enforcement tier MUST be inspectable. A grant suppresses prompts only while its exact resource, policy, workspace/content revision, principal, and expiry bindings remain valid. External paths/network, installs, credentials, deployment, destructive filesystem/Git actions, and unavailable required enforcement remain outside implicit allow. User-confirmed run-scoped reduced approval remains optional and cannot cover catastrophic actions (`ARCH/12`, `DEC-073`, `DEC-075`).
- `REQ-AUDIT-001` — Every security-relevant effect MUST receive a stable `effect_id`, a durable prepare record before execution, and exactly one terminal outcome receipt (`completed | denied | failed | unknown`) linked to that ID; lifecycle entries may additionally exist. A later reconciliation of terminal `unknown` MUST append a linked reconciliation fact and update only the derived status projection; it MUST NOT rewrite or append a second terminal receipt. A runtime reconciliation MUST detect a prepared effect without a terminal receipt, a terminal receipt without an intent/Thread fact, and a duplicated terminal receipt. A class census is a separate static coverage check and does not prove per-effect completeness (`DEC-031`).
- `REQ-AUDIT-002` — The audit log MUST be tamper-evident via a hash chain plus periodic Merkle roots, with a verification command that reports any added, removed, reordered, truncated, or modified entry; the command MUST state precisely what it does and does not prove.
- `REQ-AUDIT-003` — Secrets MUST be redacted from audit entries.
- `REQ-AUDIT-004` — Root authentication MUST be non-disableable and its algorithm/key owner MUST be explicit. The current BLAKE3 keyed MAC is local verification only and MUST NOT be described as a public-key signature. Roots MUST be anchored at a declared level: **`local-sink`** (target default) — locally authenticated roots appended to a distinct, ownership- and mode-validated append-only sink outside the audit store root; or **`off-box`** — roots with independently verifiable public-key proof or a trusted counter-signature recorded off-host, required for any deployment that declares an off-box trust requirement. A configured-but-unreachable sink MUST fail closed: the evidence gate fails, and the run MUST NOT degrade to a weaker level presented as the configured one. **`local-trust`** (no sink) is permitted only as an explicit, acknowledged posture. The trust assumptions and strength of each level MUST be documented per deployment.
- `REQ-AUDIT-005` — The audit MUST provide a first-class class-coverage census and a per-effect reconciliation report over stable effect IDs. Both MUST fail loudly on gaps; the census alone MUST NOT be presented as runtime completeness evidence.
- `REQ-AUDIT-006` — Where an effect is represented in more than one append-only store (Thread log, audit chain, analytics ledger), the stores MUST satisfy a documented cross-store consistency invariant: a security-relevant effect is complete only once durably chained in audit, cross-store references carry the authoritative store sequence, and cross-store ordering MUST NOT be inferred from wall-clock time.
- `REQ-AUDIT-007` — Every anchoring level MUST state, and `audit verify` MUST render, precisely what it detects and does not detect: tamper-evidence covers modification of **already-anchored** history by a principal that does not hold the anchoring credential; it does NOT prove content authenticity, does NOT detect fabrication by a principal holding local write access (and, for `local-sink`, sink-write access), and does NOT cover entries written after the last anchored root. Only the level names `local-trust`, `local-sink`, and `off-box` may describe the evidence, and `local-sink` MUST NOT be presented as `off-box`.
- `REQ-AUDIT-008` — Audit history, replay, verification details, and exports MUST use an explicit read/export authorization policy scoped to the requesting actor, Run/Thread, and destination. Access MUST be auditable without recursively requiring the same export path; credentials and unredacted payloads MUST remain excluded.
- `REQ-AUDIT-009` — Audit entries MUST carry a globally monotonic `audit_seq` plus `segment_id` and `segment_seq`; per-Thread ordering remains owned by the Thread log. Verification MUST be read-only. Repair MUST be a separately authorized, auditable operation that preserves the corrupt source bytes and records the repaired chain as a new recovery artifact; it MUST NOT rewrite evidence in place or claim that repaired history was authentic.
- `REQ-AUDIT-010` — Audit writers MUST serialize across processes with an OS-backed lock acquired before reading or reconciling the head, segments, roots, or sequence. A process-local mutex MUST NOT be treated as cross-process serialization. Lock loss MUST fence further writes until state is reconciled.
- `REQ-AUDIT-011` — Audit reads MUST distinguish a genuinely empty store from missing, malformed, inaccessible, or incompletely enumerated state. Verification, replay, and census MUST return a typed failure rather than a clean/empty result when required files or directory entries cannot be read. Ordinary writer startup MUST refuse malformed or torn state for explicit recovery; it MUST NOT silently replace a corrupt head or truncate a segment.

## SESS

Replay, checkpoint/rewind, fork, and portable export MUST verify refs and surface missing/corrupt/unsupported data as typed unavailable, never empty content. Read-only queries/listing MUST be byte-preserving, MUST NOT trigger repair or truncate a torn tail, and MUST disclose incomplete enumeration/unreadable Threads rather than omit them. Recovery is a distinct operation that preserves the original bytes and reconciles event/effect IDs. A writer MUST hold a single cross-process owner lease/fence and stale epochs MUST be rejected. Thread retention/deletion MUST follow an explicit policy and preserve pinned checkpoints, evidence, exports, quarantined tails, and audit receipts. Long-horizon runs MUST use a crash-durable profile and MUST stop or wait before exhausting the reserved capacity needed to record cancellation, reconciliation, and a truthful handoff.
- `REQ-SESS-007` — Users MUST be able to search committed, user-visible conversation content across all Threads they are authorized to read and within one selected Thread. Search MUST support case-insensitive whole-token matching, quoted contiguous token phrases, result-to-message navigation by immutable `ThreadId` + `MessageId` + sequence, and optional Thread/project/date/role filters. A rename MUST NOT orphan message hits; results MUST show the current Thread title, while previous titles MAY remain searchable as aliases until the Thread is deleted. A title-only match MUST be distinguishable from a message match and MUST NOT invent a message target. Search MUST index only the committed message revision currently displayed and text extracted by a versioned deterministic rule from user-visible parts; hidden reasoning, uncommitted events, non-text/binary content, and transient deltas MUST be excluded. Tool output MUST be indexed only when persisted as displayable content and enabled by the user's preference; disabling it MUST hide existing indexed results/snippets immediately even if purge is pending. When title and message body both match, do not emit a redundant title-only row; attach title context to message hits. Stable pagination MUST have a total order across message/title hit kinds and use keyset cursors bound to query/filter/extractor/index/catalog generations. `COMPLETE` coverage MUST prove the stable authorized Thread scope is fully enumerated and each committed head is indexed; bounded samples alone are not proof. The index is derived from verified committed Thread events, versioned/rebuildable, and MUST expose stale/partial/corrupt/unreadable/loading coverage rather than report incomplete data as “no results.” Queries MUST be local, bounded, cancellable, safely parsed, and must not call a model or network service. Search snippets/navigation MUST revalidate referenced events before display; retention/deletion MUST remove derived index content and title aliases. (`ARCH/07`, `ARCH/06`, `ARCH/18`, `DEC-065`.)
- `REQ-SESS-008` — HorizonCode MUST use one stable internal `ThreadId` for each durable agent conversation across process restarts, worker-execution retries under the same Attempt, provider/model changes that continue that conversation, and UI reconnections. A changed task strategy creates a new Attempt and its own Thread; it MUST NOT rewrite prior conversation identity or history. A `WorkerExecution` identifies one live process/peer incarnation; ACP/provider `SessionId`s are external adapter bindings and MUST NOT create a second HorizonCode conversation identity. Thread parent/child relationships MUST remain distinct from the Run Task DAG. Migration from session-named storage MUST preserve legacy IDs, committed event bytes, message identities, cursors, and unknown fields; MUST be versioned, restart-safe, idempotent, and recoverable from a separately verified generation; MUST NOT rewrite a hash-chained source generation in place. Worker/thread completion MUST NOT establish Task pass. (`ARCH/07`, `ARCH/25`, `DEC-069`.)

## SEC (threat model — consolidated in `ARCH/22-SECURITY.md`)

Hard requirements derived from the threat model. Each is observable and falsifiable;
`ARCH/22` names the threat rows each discharges.

- `REQ-SEC-004` — Every filesystem target MUST be canonicalized (symlinks/junctions, platform case rules, long paths) before policy evaluation, and re-canonicalized at use; a canonical mismatch between check and use MUST deny the operation, and no policy decision may be made on a non-canonical path.
- `REQ-SEC-005` — Every filesystem effect MUST be checked at the last responsible enforcement boundary. In-process file operations MUST use handle-relative, no-follow APIs with revalidation at use where the platform exposes them; spawned processes MUST use the selected OS confinement backend. A caller-side path check or lexical pre-scan alone MUST NOT be described as kernel containment. Each backend MUST state which escapes it can prevent, its tested tier, and residual limits; a caller requiring a stronger guarantee MUST be refused rather than silently downgraded.
- `REQ-SEC-006` — Process invocation MUST use argv-based spawn with an explicit environment allowlist and MUST NOT concatenate untrusted values into a shell script. An explicitly requested shell-script tool MAY pass its complete, model-supplied script as one `sh -c` argument only after showing and authorizing that exact script and applying an enforceable confinement profile. It MUST be classified and audited as shell execution, not described as inert argv execution. No HorizonCode-resolved credential may be forwarded to a child (`DEC-031`).
- `REQ-SEC-007` — All HorizonCode-owned HTTP requests MUST use one mediated egress that authorizes the resolved address and each redirect hop; private, link-local, loopback, and reserved ranges are refused unless an explicit higher-trust policy grants that target. On an origin or route change, authorization, cookie, proxy-authorization, and other destination-bound credentials are stripped by default and may be re-added only from a credential explicitly scoped to the newly authorized destination. Child processes MUST have network denied by an independently proven confinement mechanism or use a forced egress broker that the child cannot bypass. A profile whose backend cannot prove either condition MUST refuse network-restricted execution rather than claim mediation (`DEC-031`).
- `REQ-SEC-008` — External content (repository text, fetched pages, tool output, skill/plugin bodies, instruction files, sub-agent receipts, peer frames) MUST be labeled and framed as untrusted data and MUST NOT be able to create a rule, ticket, grant, or decision; it MUST NOT be able to create, widen, or satisfy a **network** grant either, so a network permission is granted only by a user act and is then enforced at the confinement tier's declared `network_guarantee_level`, with a required level the tier cannot provide refused rather than approximated (`DEC-026`, `DEC-027`); any action it motivates MUST re-enter the guard-authorized path. Network guarantee describes reachable network paths, not denial of the `socket()` API itself; local IPC such as `AF_UNIX` is a separate resource boundary and MUST be separately scoped.
- `REQ-SEC-009` — Values resolved by `CMP-secrets` MUST NOT be intentionally placed in model prompts, context, child environments, diagnostics, audit/analytics fields, or exports. Any bounded text path that can echo a brokered value MUST apply exact known-value and configured recognized-pattern redaction before display or persistence, and refuse the operation if that redaction fails. Canary tests MUST cover brokered values across each path. This does not claim perfect detection of unrelated or transformed secrets already present in workspace/provider/tool text; those remain an explicit residual, with arbitrary free text excluded or handled through bounded artifact/access policy (`ARCH/14`, `ARCH/22`).
- `REQ-SEC-010` — Guard authorization MUST NOT imply reach: the confinement layer MUST be able to deny an already-authorized effect, and a backend that cannot apply the requested profile MUST refuse the effect rather than run it unconfined.
- `REQ-SEC-011` — The agent process MUST run with no new privileges and an empty effective/permitted capability set, MUST NOT run elevated by default, and any elevation MUST require an explicit, audited user act.
- `REQ-SEC-012` — An audit append failure MUST fail the governed action closed; `audit verify` MUST detect added, removed, reordered, truncated, and modified entries; the coverage census MUST fail loudly on any uncovered declared effect class; cross-store reconciliation gaps MUST be surfaced, never merged.
- `REQ-SEC-013` — Every session and run MUST carry enforceable ceilings for steps, tool calls, wall-clock, tokens, cost, retries, output bytes, and concurrency; exhaustion MUST fail closed and be audited; no ceiling may be raised by a model-, peer-, or content-supplied value. No feature flag, environment variable, build profile, or user/project configuration may disable a finite retry/attempt ceiling or create an unbounded retry loop.
- `REQ-SEC-014` — A sub-agent's or peer agent's effective authority MUST be the intersection of the parent's ceiling and its declared scope; a receipt or peer response MUST NOT widen authority; any path, resource, or service a peer proposes MUST be re-authorized locally, and an approval MUST be bound to the specific requester and action.
- `REQ-SEC-015` — A skill, plugin, hook, or MCP server MUST be disabled until explicitly enabled, MUST be pinned by version and a content hash over a normalized file-set manifest, and its content MUST be treated as untrusted data; a pin mismatch or unresolvable provenance MUST refuse to load.
- `REQ-SEC-016` — Extension-provided processes MUST run under a confinement profile that denies ambient network to the level the tier **declares** under `DEC-026` — `enforced`, `capability`, `best_effort`, or `none`, each with its mechanism and its residual — and scopes writes to the workspace; the declared level, mechanism, and residual MUST be recorded in that extension's acceptance record (`network_guarantee_level` / `network_mechanism` / `network_residual`) and surfaced wherever the extension's confinement profile is presented, and a caller requiring a level the tier does not provide MUST be refused rather than downgraded (`DEC-027`). Package extraction MUST be confined to the package root with declared file-count and byte budgets; a hook MUST NOT be able to loosen policy, and a hook failure MUST leave the action at its original authority.
- `REQ-SEC-017` — Externally fetched provider/model metadata MUST be schema-validated, data-only, provenance-stamped, content-hashed, and unable to grant credentials, auth methods, adapter code, or arbitrary endpoints. The only default-refresh exception is the explicitly named OpenCode catalog/Go source from fixed, validated HTTPS origins under `DEC-060`; generic enrichment remains opt-in, offline-primary remains available, and refresh MUST NOT mutate pinned evaluation fixtures or active route snapshots. Third-party marks are not redistributed (`DEC-021`, `DEC-060`).
- `REQ-SEC-028` — External editor and patch reconciliation MUST preserve raw-byte base digests as the final compare-and-swap authority. CRLF/LF normalization MAY assist deterministic hunk alignment, but MUST NOT silently discard trailing whitespace or change the authority digest. A merge MUST use the exact captured base, uniquely anchor non-overlapping changes, preserve the user's current bytes/format where possible, validate the resulting patch, and compare-and-swap against the current digest. Ambiguous/overlapping hunks require review; no fuzzy line-number guess may authorize a write (`DEC-074`).
- `REQ-SEC-029` — Hook execution MUST use a bounded typed IPC contract, explicit source-digest trust for project hooks, scrubbed/allowlisted environment, timeout and input/output/resource ceilings. Hook output may observe or make policy stricter but MUST NOT grant permission, suppress required audit, alter canonical verifier results, or bypass guard/confinement. A modified hook definition invalidates prior trust (`DEC-077`).
- `REQ-SEC-030` — A direct edit, editor save, checkpoint, rewind, or diff operation MUST preserve the user's Git index, reflog, and commit history unless the user explicitly requests a guarded stage/commit operation. Checkpoint/rewind storage MUST be HorizonCode-owned and MUST NOT create temporary commits or mutate the user's `.git` state (`DEC-074`).
- `REQ-SEC-018` — Every state, config, policy, and cache directory MUST be validated for ownership and mode before use, and a failed validation MUST fail closed rather than proceed.
- `REQ-SEC-019` — A policy, config, state, or lock path that resolves through a symlink or junction outside its expected root MUST be refused; lock, head, and temporary files MUST be created with no-follow and exclusive-create semantics.
- `REQ-SEC-020` — A referenced security-relevant effect with no audit entry, and an audit entry with no referenced session fact, MUST each be reported as an incident with an owner and MUST NOT be silently reconciled.
- `REQ-SEC-021` — Unconfined execution MUST be unreachable unless enabled by an explicit, audited, one-use, expiring user act bound to exact work/effect scope; project/agent configuration MUST NOT enable it. The grant MUST be unavailable unless a distinct worker identity or isolated VM keeps controller state, credentials, canonical Run/Thread/audit state, and operator-control IPC outside the worker view. The active reach and lost-protection posture MUST be displayed before confirmation and in every surface that can present an effect. This grant does not claim a sandbox/containment guarantee for paths in its declared scope (`ARCH/13`, `ARCH/22`).
- `REQ-SEC-022` — Malformed or hostile tool input, protocol frames, configuration, patch text, and package members MUST be rejected with typed errors: no panic, no unreported partial application, and no allocation or loop driven by an untrusted size or count field. Multi-file patch operations MUST preflight all hunks and base hashes before any mutation; commit is all-or-nothing where the filesystem permits it. If a crash interrupts commit, recovery MUST enumerate every already-applied file and reconcile or roll back before the task can proceed (`DEC-031`).
- `REQ-SEC-023` — Structural boundary properties MUST be enforced by automated checks that fail the build: no effect path without a guard assertion and an audit append, no permission evaluation outside the guard, and no direct network-client construction above the mediated egress layer. A route that requires managed egress MUST receive a non-defaultable policy/backend requirement; default-unmanaged constructors, direct factories, deprecated compatibility paths, and runtime fallbacks MUST be inventoried and proved unreachable for that route or fail closed. No fallback may turn a required enforcement level into a weaker one.
- `REQ-SEC-024` — The actual anchoring level (`local-trust | local-sink | off-box`) MUST be surfaced wherever audit history is presented. Neither local level may be presented as independent off-box verification; the claim boundary for fabrication and the unanchored tail MUST be shown. A configured-but-unreachable required anchor MUST fail closed rather than silently degrade.
- `REQ-SEC-025` — Exactly one component evaluates path policy (`CMP-guard`) and exactly one applies path reach (`CMP-sandbox`); no other component may return a path allow/ask/deny or be the sole path control. `exec.run` rules MUST match the command token prefix only and MUST NOT carry path-shaped resources; a path named by a shell argument is expressed as an `fs.*` resource so it is evaluated by the same path matcher. A command argument naming a path outside the granted roots, not deny-globbed and not explicitly allowed, MUST resolve to `ask` at minimum; a deny-glob or protected-subpath match MUST resolve to `deny`; and a tier that cannot enforce the required reach MUST refuse the effect. Acceptance records MUST distinguish caller-side checks from child-process OS confinement.
- `REQ-SEC-026` — The execution controller's canonical Run/Thread state, audit store, operator-control socket/capability, policy snapshots, and credential broker MUST remain outside every model/worker/peer/plugin process view, including any broad-access execution profile. Worker processes MUST NOT mint user/operator approval, alter durable budgets or run evidence, or reach the controller control API by invoking the CLI or forging prompt/protocol content. Controller mutation APIs MUST NOT accept caller-authored actor/principal enums, trust flags, approval booleans, or authentication results; they MUST validate a sealed, controller-minted, operation-scoped context bound to run, fence, expiry, and one-use delivery. Operator identity and scope MUST come from authenticated first-party ingress, not caller-provided fields, command arguments, environment variables, config, model output, or peer receipts. A raw ACP connection/session ID MUST NOT count as authentication or proof of user interaction; only an explicitly trusted interactive connector with a verified identity/control scope may mint an ACP approval receipt. The selected backend MUST prove the state/control boundary for the process tier; otherwise the profile MUST be unavailable and multi-hour completion MUST remain unverified. The trusted operator UI/CLI/ACP connector is in the trusted computing base and is the only path that can approve a goal or elevate a bounded preference.
- `REQ-SEC-027` — OAuth/device-code integrations MUST use a HorizonCode-owned registered client and the provider's documented authorization flow, least scopes, state/PKCE where supported, and OS-backed secret storage. Token, refresh, and revoke endpoints MUST come from reviewed provider configuration and pass the same parsed-origin/egress policy as other credential-bearing requests; ambient environment overrides MUST NOT redirect them or substitute client identity unless an explicit, validated local administrator configuration enables a reviewed endpoint. A provider that requires a proprietary client identity, prohibited client, unsupported consent mechanism, or credential extraction from another application MUST be marked unavailable until an authorized integration exists; copying an application's local credential store or impersonating it is forbidden.

## VER (verification — strategy in `ARCH/23-VERIFICATION.md`)

Requirements about how claims become evidence. `ARCH/23` owns the layers, the P1
acceptance matrix, the determinism/flake policy, the budgets, and the release gates.

- `REQ-VER-001` — Every capability MUST declare its evidence layers and its acceptance-record path; a capability without an acceptance record MUST report readiness as unverified, and the state "implemented but unverified" MUST be labeled wherever the capability appears.
- `REQ-VER-002` — Deterministic unit and contract tests MUST inject time, identifiers, randomness, home/state directory, environment, and transport; they MUST NOT depend on a live model or external network. Platform acceptance tests MAY depend on the actual host OS, kernel, filesystem, and declared confinement backend, but MUST record these inputs and MUST NOT be represented as portable deterministic tests.
- `REQ-VER-003` — Provider and HTTP behavior MUST be exercised against mock or in-process transports and loopback servers bound to an ephemeral local port; a test that attempts any non-loopback connection MUST fail.
- `REQ-VER-004` — The full suite MUST pass at least five consecutive clean runs on the merge gate, and process- or platform-sensitive suites at least twenty repetitions; a quarantined test MUST record an owner, reason, issue, and expiry, and a quarantined security-relevant test MUST block release.
- `REQ-VER-005` — Sandbox containment MUST be proven by executable tests per supported tier: denied-path read denial, write denial outside writable roots, rename-out-of-deny-set denial, the tier's **declared** network guarantee level, applicable capability restrictions, and fail-closed behavior when the backend is unavailable; a skipped sub-check MUST fail the run. Network tests assert actual reachable paths and the documented residual for the selected mechanism; they MUST NOT substitute a syscall assertion for a reachability claim. Allowlist precision is accepted only for a backend with an unbypassable broker. The record stores `network_guarantee_level`, `network_mechanism`, and `network_residual`; `ACC-P1-01(d)` is the evidence check and its refusal sub-check is `ACC-P1-01(j)`. A caller's required network level is a separate policy input; a tier that cannot meet it MUST refuse rather than degrade.
- `REQ-VER-006` — Guard precedence MUST be proven by a committed decision table covering deny/ask/allow ordering, the outer deny ceiling, the plan-mode ceiling, the fail-closed unmatched effect, rule-layer fallback, and exactness of the persisted "always allow" pattern; a mismatch between the evaluator and the table MUST fail.
- `REQ-VER-007` — The approval path MUST be proven end-to-end through ACP's baseline `session/request_permission` method: exactly one request per decision; schema-valid option kinds with opaque option IDs round-trip unchanged; an unsupported method, malformed response, disconnect, or timeout fails closed; replies are recorded and correlated to the originating effect; cancellation is distinct from user rejection; requests are serialized per session without blocking cancel/control; and rejection ends the turn declined without becoming model-facing output.
- `REQ-VER-008` — Audit verification MUST be proven with a negative control: a tampered copy in which an entry is added, removed, reordered, truncated, and modified MUST each be detected with the failing sequence named; the coverage census MUST fail on an injected uncovered class; a redaction canary MUST be absent from every entry, root, verify output, replay output, and export.
- `REQ-VER-009` — Session replay MUST be byte-deterministic for a given committed segmented event stream and head, verified by golden transcripts and a real kill/restart matrix with zero divergence. Read-only inspection MUST preserve all source bytes; interrupted-tail handling MUST use the explicit preservation- and effect-reconciliation recovery contract in `ACC-P1-06`/`ACC-P1-12`. A stored format newer than the build MUST be refused typed with no partial decode.
- `REQ-VER-010` — Compaction MUST be gated by a pre-registered retrieval probe evaluated after each compaction; a probe regression MUST block the strategy change, a compaction boundary MUST never split a tool call from its result, and an overflow MUST trigger exactly one compact-and-retry.
- `REQ-VER-011` — Every turn terminal state MUST map to exactly one documented headless exit code, the numeric mapping MUST be documented in `--help`, and a test MUST fail if the implementation and `--help` disagree.
- `REQ-VER-012` — Each performance budget MUST be measured by a repeatable procedure with a recorded machine baseline; a budget without a recorded baseline MUST be reported as unmeasured and MUST NOT be reported as passing, and no budget may be met by weakening a security control.
- `REQ-VER-013` — A release MUST be blocked unless the license allowlist gate, provenance records, the generated third-party notices bundle, a zero-quarantine multi-run suite streak, containment acceptance for every supported tier, audit verification plus class census and per-effect reconciliation with the required reachable anchor, the exit-code contract, session/artifact migration and integrity chains, evidence-bound product-claim review, a clean fuzz cycle, and per-requirement traceability all pass. Every route that advertises automatic output-truncation recovery MUST pass its route-specific conformance record. A multi-hour-autonomy claim additionally requires `ACC-H1-01..10`.
- `REQ-VER-014` — Every acceptance record MUST be bound to a build identifier, the exact commit, the platform, the tier, and the backend; a record MUST NOT be presented as evidence for a different build, platform, or tier.
- `REQ-VER-015` — No surface, document, or status view may present a capability as ready, verified, contained, or audited without a linked acceptance record; mocks, previews, catalog entries, and unit-test results are explicitly not acceptance evidence.
- `REQ-VER-016` — Parsers for untrusted formats (protocol frames, configuration, tool input/output, patch text, package archives, catalog records) MUST have fuzz targets; a crash, panic, or unbounded allocation found by fuzzing MUST block release, and the minimized input MUST be committed to the corpus.
- `REQ-VER-017` — A fixed defect MUST land with a regression test that fails without the fix; a fix without a regression test is not complete.
- `REQ-VER-018` — An eval-gated capability MUST NOT ship before the harness that judges it can be run at the moment it ships; a gate that can only be satisfied retroactively does not satisfy this requirement.

## MEM (persistent memory)

- `REQ-MEM-001` — The agent MUST maintain a persistent project/user memory store distinct from Threads, with bounded size and an explicit compaction policy.
- `REQ-MEM-002` — Memory writes MUST be attributable and inspectable; the agent MUST NOT silently persist model guesses as facts.
- `REQ-MEM-003` — Memory MUST be injectable as a typed context source.
- `REQ-MEM-004` — Memory MUST support separate user-global and project scopes with no cross-project leakage. Explicit user-directed saves may create a reviewable candidate. Automatic extraction MUST be opt-in by default; automatic acceptance MUST remain off. Global scope is for user preferences/work habits, while repository facts and decisions default to stable project identity and carry source revision/provenance. `/memory` MUST inspect, search, approve/reject, supersede, export, and purge records by scope; disabled retrieval MUST be distinct from deletion.
- `REQ-MEM-005` — Every worker context MUST be assembled from an explicit, bounded `ContextPacket` bound to its `ContextEpoch`. A child MUST receive its task contract, approved constraints/acceptance criteria, effective instruction and permission snapshots, and only referenced repository/context artifacts selected for that task. Default child history fork is `none`; parent transcript, sibling transcript, and parent auto-memory MUST NOT be copied implicitly. A bounded fork or transcript excerpt requires explicit source references, a size budget, and policy authorization; a full parent-history fork is unavailable to external agents and MUST NOT cross a trust/data boundary implicitly. Missing, stale, or excluded context MUST remain visible to the worker as missing/unknown, not silently substituted. Replaying the same dispatch within an unchanged context epoch MUST reuse the pinned packet/digest and MUST NOT duplicate injected context; intentional refresh requires a new epoch or explicit invalidation. (`ARCH/09`, `ARCH/16`, `ARCH/25`, `ARCH/33`.)
- `REQ-MEM-006` — Per-agent memory MAY be enabled as a separately scoped namespace under the existing user/project store, keyed by stable `AgentProfileId` and repository identity where applicable. Its effective policy MUST be the intersection of user/managed policy, Run consent, profile configuration, adapter capability, and data-egress scope. Default profile memory sharing is `none`; project configuration cannot widen it. Context construction may retrieve only accepted, current, scope-authorized, bounded records selected for the child task; it MUST pin record IDs/revisions/digests to the child's `ContextEpoch`. Parent and sibling memory is not implicitly inherited. Child memory writes MUST enter the existing reviewable candidate flow; a child cannot directly accept, re-scope, alter provenance, or delete accepted memory. Retrieved content remains untrusted context, never instruction authority, permission, or verification evidence. (`ARCH/16`, `ARCH/18`, `ARCH/27`, `ARCH/33`.)
- `REQ-MEM-007` — Memory capture, retrieval, search, export, purge, and child injection MUST use one canonical `ProjectIdentity` resolver and one immutable `ContextScope` derived from the admitted Run workspace or direct Thread's pinned workspace and effective settings. A child worktree MUST inherit the Run's project identity rather than infer identity from its temporary path or basename. Identity changes/aliases MUST be explicit and auditable; ambiguous identity MUST fail closed for project-memory retrieval and remain visible. The resolver MUST NOT persist or transmit credential-bearing remote URLs as identity material. (`ARCH/07`, `ARCH/09`, `ARCH/18`, `ARCH/33`.)

## SKILL

- `REQ-SKILL-001` — Skills MUST be discovered from `SKILL.md` files with `name` + `description` frontmatter; discovery roots MUST include the user scope and the project scope.
- `REQ-SKILL-002` — Skill routing MUST be description-based with progressive disclosure: only metadata is resident in context until invocation; the body loads on demand; resources and scripts load lazily.
- `REQ-SKILL-003` — Externally sourced skills MUST be pinned by version/hash before use; a pin mismatch MUST refuse to load until re-pinned.
- `REQ-SKILL-004` — A skill's declared `allowed-tools` MUST be treated as an approval hint, never as a sandbox or a grant.
- `REQ-SKILL-005` — User-invocable skills MUST remain addressable when a name collides with a built-in command or another skill. The built-in retains its bare command. A colliding skill receives a deterministic command key built from its canonical source identity and skill name, using `/<source-kind>:<source-id>:<skill-name>` (for example `/plugin:acme:login`); if the same source contributes duplicate skill names, append the canonical relative skill path as escaped path segments. Source IDs MUST be stable, URL-safe identifiers assigned by the source/registry, never discovery order or display labels. Registration MUST reject any residual key collision and report both sources; no registration order may shadow or replace an entry. Suggestions and help MUST expose the full source qualification. `/skill` and `/skills` remain manager-navigation commands; invoking a skill is a distinct explicit route. Invocation MUST revalidate the selected source identity, canonical path, and content digest, and skill content remains untrusted instructions that cannot grant tools, permissions, or completion authority (`DEC-080`).

## ANALYTICS

- `REQ-ANALYTICS-002` — Cost and usage MUST distinguish provider-reported actual, estimate, included-plan observation, and unknown, and MUST carry a pricing/usage source version. Unknown pricing or usage MUST be reported as unknown, never fabricated or normalized to zero. An absent token/cache/reasoning field is `UNKNOWN`, not zero; partial usage reported before a failed/cancelled stream MUST be reconciled exactly once.

Provider-reported cache-read and cache-creation/write usage MUST remain distinct, preserving raw provider fields and unknown values; route-specific pricing rules determine monetary interpretation (`ARCH/20`, `DEC-034`, `DEC-075`).

## LONG HORIZON CONTROL (integrated design in `ARCH/25-LONG-HORIZON-CONTROL.md`)

- `REQ-HORIZON-005` — The original user request, confirmed requirements, assumptions, exclusions, examples, technical decisions, and specification revisions MUST be stored separately with provenance. A change to user-visible behavior MUST create a new approved specification version and invalidate affected tasks and evidence.
- `REQ-HORIZON-006` — A run, session, turn, task, attempt, external-agent attempt, workspace, and verification record MUST have distinct identities and lifecycles. Only a task with independent `PASS` evidence bound to the current specification digest and exact tested repository revision may satisfy a downstream dependency.
- `REQ-HORIZON-007` — One deterministic controller MUST own dispatch, atomic budget reservations, retry accounting, lease fencing, recovery classification, and stop decisions. Completion MUST be derived from mandatory acceptance evidence; budget exhaustion, no ready task, disconnection, and waiting for a user MUST remain distinct outcomes.
- `REQ-HORIZON-008` — Before replaying an interrupted effect, the controller MUST reconcile its intent, authorization, workspace state, audit receipt, and external provider/PR outcome. Unknown or non-idempotent effects MUST wait for investigation; starting a new Thread, protocol Session, or WorkerExecution MUST NOT reset managed Attempt counts or spend.
- `REQ-HORIZON-009` — A delegated agent MUST have an HorizonCode-owned attempt record with peer identity, protocol/version and capability snapshot, external session ID if supplied, event cursor, workspace/base revision, authority scope, usage provenance, and opaque-state limitations. Unreported nested work or usage MUST be displayed as unknown.
- `REQ-HORIZON-010` — Final integration MUST reverify the combined revision against current specification and original confirmed intent. A worker's completion text, tool success, and isolated-worktree tests MUST NOT by themselves mark the run complete.
- `REQ-HORIZON-011` — A multi-hour run MUST survive UI client disconnect without being cancelled. A detached run MUST have a supervised controller process and authenticated same-host attach path (restricted to the local OS user by default) that returns a sequence-stamped snapshot followed by ordered event replay; a cursor gap MUST resnapshot. Remote attachment is a separate capability requiring an explicit authenticated network protocol and acceptance. A stopped host MUST be shown as last-known state, never as active progress.
- `REQ-HORIZON-012` — A permission request raised by a child or external worker MUST be correlated to the owning Run and requester, durably bound to the authenticated control session and exact connection that receives it, forwarded to an authorized interactive surface, and returned to the original request. An answer from another connection is a typed refusal; closing the originating connection invalidates its unanswered challenges before teardown. Every challenge has a finite TTL and bounded queue/resource use. Missing mapping, unavailable client, disconnect, cancellation, or expiry MUST produce a typed denial/cancellation and settle the child; it MUST NOT disappear or wait indefinitely. A worker or peer receipt cannot establish that the resource shown to the operator is still the resource about to be changed; see `REQ-GUARD-006`.
- `REQ-HORIZON-013` — Event delivery to clients MUST use bounded queues and durable sequence/cursor replay. Slow-client handling MUST emit an explicit gap/resnapshot condition or disconnect with a recoverable cursor; events MUST NOT be silently dropped, nor may an unbounded queue exhaust process memory. Request lanes MUST isolate unrelated control operations so one hung request cannot wedge all work.
- `REQ-HORIZON-014` — Dispatch MUST define fairness and starvation bounds across interactive steering, queued user work, verification, and background tasks. Priority MUST NOT allow repeated background or verification work to starve user control; pause/cancel and approval responses receive bounded service time.
- `REQ-HORIZON-015` — Before every automatic continuation, the controller MUST evaluate a durable progress signature that includes objective/spec version, task/evidence transitions, repository/workspace revision, external-event cursor, failure fingerprint, and strategy. Model text, tool-call count, heartbeat, repeated reads, or compaction alone MUST NOT count as progress. Configured finite no-progress, repeated-batch, and attempt ceilings MUST survive restart, compaction, model changes, and peer-session replacement; crossing a ceiling MUST pause or stop dispatch with an inspectable reason rather than launch another identical attempt. An explicit user action is required to resume a controller-paused run.
- `REQ-HORIZON-016` — Waiting for a future time, user input, approval, or external event MUST persist as a durable wait condition and consume no model inference while no work is eligible. A timer/event wake MUST be idempotent and sequence-stamped; restart MUST reconcile missed/duplicate wakes before dispatch. The wait consumes elapsed-time allowance only as configured and MUST NOT imply progress while asleep. Polling an external service is a separate permissioned, budgeted action, not an implicit wait implementation.
- `REQ-HORIZON-017` — Explicit user pause MUST fence all new dispatch and automatic continuation, persist across process restart and compaction, and require an explicit resume action. In-flight actions MUST be cancelled where supported and reconciled before the run is reported paused. A pause/cancel command MUST preempt model-generated work through a reserved control lane; model output cannot veto it. Its acknowledgement/status receipt MUST have a deadline independent of the operation being cancelled; the command returns a bounded `REQUESTED`/`RECONCILING` receipt promptly and terminal settlement is queried by stable delivery ID. `PAUSED` is distinct from condition-driven `WAITING`, hard-bound `STOPPED`, terminal `CANCELLED`, and successful `COMPLETED`.
- `REQ-HORIZON-018` — A user input that unambiguously requests pausing, cancelling, or stopping an active run MUST be routed through the controller's priority control lane before another model continuation is dispatched; it MUST NOT depend on the worker obeying conversational text. If the requested action or target is ambiguous, the controller MUST fence automatic continuation and ask which control action/target the user intends. Control-intent parsing, the selected run, and the resulting fence/decision MUST be durable and visible; an ordinary discussion of stopping that is not an instruction MUST remain ordinary input.
- `REQ-HORIZON-019` — After all mandatory criteria pass and the terminal completion event is durably committed, a foreground client MUST return promptly with the run outcome. Non-critical indexing, analytics aggregation, and checkpoint maintenance MUST be reported as bounded `maintenance_pending` work and MUST NOT silently hold a completed foreground request. If a durability-critical write has not completed, the run MUST remain nonterminal and the client MUST show the exact wait/recovery state; it MUST NOT report completion early.
- `REQ-HORIZON-020` — Creating a goal draft MUST only persist the original request and must not invoke a model, repository tool, or peer. A separate explicit prepare action MAY invoke a bounded planner and revision-pinned, read-only repository discovery under its own resource allowance; it MUST NOT dispatch coding workers, write tools, or external side effects. Before coding/task dispatch, the user MUST approve the exact displayed `spec_digest`, task-graph digest, plan digest, workspace/base revision, execution route, permission scope, budget, and verification/recovery reserve through an explicit start action. The controller MUST revalidate unresolved consequential ambiguity, graph acyclicity, capability and policy eligibility, workspace/base revision, and atomic run/verification/recovery budget reservations. A stale preview, unresolved blocking question, failed reservation, or duplicate delivery MUST not create duplicate budget or work; preparation and start receipts and recovery MUST be idempotent. TUI/CLI use the typed control service; ACP agent servers MAY use negotiated `elicitation/create` or the exact one-use digest-bound control receipt intercepted before model dispatch, but only through a configured trusted interactive connector with verified identity/control scope. ACP connections/session IDs alone MUST NOT authenticate the operator or prove a human saw or accepted the prompt. ACP peer elicitation when HorizonCode is an ACP client is untrusted peer input. Only a trusted operator ingress may mint approval: model, tool, peer, plugin, ordinary CLI subprocess, and system recovery principals MUST be unable to mint or replay it, even if they can construct the command/payload. Generic “yes”, a tool permission response, or a worker's claim MUST NOT approve goal activation.
- `REQ-HORIZON-021` — Opening goal-start review MUST persist an expiring, one-use `GoalApprovalChallenge` before presenting a canonical review bundle; it MUST bind challenge/run/goal IDs, all approved digests, authenticated principal/control-session/connection, surface, expiry, and review/response delivery digests. There MUST be at most one pending challenge and one nonterminal start intent per goal; duplicate delivery with the same payload MUST return the same challenge/result, while changed payload under a reused delivery ID MUST conflict. A newer review, material spec/plan/base/route/permission/budget/policy change, additional input, disconnect or session change while pending, or expiry MUST invalidate a pending challenge. Confirmation MUST arrive through the same trusted operator control context and match the exact review-bundle digest; stale, replayed, concurrent, cross-session, declined, or cancelled responses MUST NOT activate work. Persist accepted confirmation and a one-shot expiring receipt before reserving resources; a durable accepted intent may recover across client disconnect only while the receipt remains valid and current policy/digests still match. Reservations MUST use stable idempotency keys and MUST be durably confirmed before a `GoalActivated` commit event. Dispatch MUST be derived only from that commit event through a durable idempotent outbox; recovery MUST reconcile partial reservations and uncertain launches without reminting approval or creating duplicate tasks/attempts. Receipt expiry or a material change before activation rejects the intent, reconciles/releases reservations, and requires a fresh review. Because the event log, projections, budget ledger, and process launch are not one transaction, all intermediate and unknown states MUST be explicit and fail closed.
- `REQ-HORIZON-022` — A durably accepted challenge/receipt MUST be shown as “starting” or “reconciling,” never as active/running, until `GoalActivated` is committed. The controller MUST permit only one nonterminal start intent per goal and MUST reject a new review while that intent is being reconciled. Immediately before activation, a versioned compare-and-swap MUST confirm that the reviewed policy and budget snapshots remain current; reservation failure, receipt expiry, or snapshot mismatch MUST durably reject/invalidate the intent, reconcile or release reservations idempotently, and require a fresh review. A durable `DispatchOutbox` item MUST be unique by activation/eligible-claim event and task, carry the stable attempt ID and workspace fence, and be acknowledged only against a matching supervisor/worker receipt. An unknown launch MUST block replacement attempts until the process and workspace are reconciled. Projection rebuild or client replay MUST NOT create a new approval, reservation, task, or attempt.
- `REQ-HORIZON-023` — After a control request timeout or client reconnect, an authenticated operator MUST be able to query the durable goal-start intent and reattach to its sequence-stamped events without repeating confirmation or dispatch. This read path MUST be read-only, scoped to authorized run/goal IDs, expose the last durable state and any replay gap, and be unavailable to model workers, external peers, and plugins. A lost response MUST be resolved by status/replay lookup using the original delivery ID, not by generating a new approval or retrying as a new start.
- `REQ-HORIZON-024` — A `/cancel` racing a confirmed-but-not-activated goal MUST be serialized with the `GoalActivated` commit. If cancellation wins, it MUST durably fence activation, reconcile/release all reservations idempotently, and reach `CANCELLED` only after release is confirmed. If activation wins, cancellation MUST use the normal run/task/attempt fence and reconcile dispatched or in-flight work. A disconnect MUST NOT be treated as a cancel. Duplicate cancellation delivery is idempotent, and unknown reservation/process state MUST remain `RECONCILING`, not falsely terminal.
- `REQ-HORIZON-025` — Cancellation MUST use a typed `RUN | TASK | ATTEMPT` target and matching authenticated `run:cancel | task:cancel | attempt:cancel` scope; the controller MUST resolve target ancestry, reject missing/foreign/inconsistent IDs, persist an idempotent target-scoped request and install its fence before acknowledgement. Run cancellation fences new claims globally and reaches terminal `CANCELLED` only after scoped attempts/effects are reconciled; task cancellation fences only that task, leaves independent tasks eligible, and keeps dependent tasks blocked with the cancelled dependency recorded; attempt cancellation affects only that attempt, and the parent task becomes retryable only if current retry policy, budget, and attempt limit allow it. A target already terminal remains unchanged and returns `ALREADY_TERMINAL`; unknown peer/process/effect state remains `RECONCILING` and MUST NOT be treated as successful cancellation or retried unsafely. Same-delivery/same-payload retries MUST be idempotent; changed-payload replay MUST conflict. `/stop-now` remains a distinct hard-stop action.
- `REQ-HORIZON-026` — Thread and Run/evidence payloads MUST use the shared `CMP-artifact` service with immutable, namespace-scoped `ArtifactRef`s and no implicit cross-Thread/Run deduplication. The service MUST enforce hierarchical storage reservations, bounded streaming, digest/length/schema validation, durable write-before-owner-event ordering, and reference leases held until canonical owner events are reconciled. Owner truth remains in Thread/Run/evidence canonical stores; projections/refcounts alone MUST NOT authorize deletion. Garbage collection MUST enumerate every retained Thread/Run/checkpoint/evidence/export/maintenance owner, quarantined recovery tail, migration generation, and active lease completely, abort with zero deletions on any incomplete or unreadable source, and revalidate each candidate under an exclusive artifact fence before tombstone/unlink. Cancellation, restart, corruption, migration, quota exhaustion, and unknown filesystem outcomes MUST yield typed recoverable states; a missing artifact MUST make dependent evidence `INSUFFICIENT_EVIDENCE`, never `PASS`.
- `REQ-HORIZON-027` — Canonical Thread and Run event streams MUST rotate into finite-size, sequence-contiguous immutable segments; each segment MUST be digest-linked and sealed, and the durable committed head MUST bind its sequence and digest. Replay/index rebuild MUST stream in bounded batches and validate the chain through the committed head before trusting projections. Segment rotation MUST NOT imply history deletion; active-run history and evidence MUST remain recoverable. The controller MUST reserve event bytes for each admitted step/effect and a physically allocated protected control/recovery reserve before activating a multi-hour run; logical accounting alone is insufficient. On quota or disk pressure it MUST fence new work early, preserve/use the emergency reserve, reconcile in-flight effects, and surface `WAITING`/`STOPPED` with remaining storage and the last verified commit. If the backend cannot provide the declared reservation/durability guarantees, multi-hour activation MUST be refused. No status, UI compaction, or context compaction may silently prune canonical history. Any archive/prune operation MUST be a separately authorized, digest-verified retention action that retains a recoverable manifest and never removes live evidence or required audit data.
- `REQ-HORIZON-028` — Every worker/process launch for a durable Attempt MUST first commit a durable, uniquely identified launch intent and a minimal execution receipt linked to its Run, Task, Attempt, optional HorizonCode Thread, owner epoch, workspace fence, and launch/terminal outcome. A local native child uses an OS-observable process handle/identity and bounded supervisor state; it MUST NOT require external-peer capability, usage, cursor, heartbeat, or reconciliation fields. External executions use a separate durable binding with adapter build, negotiated capability snapshot, peer/session reference, cursor, usage provenance, and explicit `UNKNOWN` reconciliation where the peer cannot be queried. The launch ID MUST deduplicate HorizonCode-owned dispatch retries. External launch idempotency MUST be capability-negotiated, never presumed: if the peer cannot deduplicate or query a launch, recovery MUST reconcile its process/peer handle, workspace revision, event cursor, usage, and pending effects before any retry; unresolved outcome remains `UNKNOWN`, writes stay fenced, and automatic retry waits for safe reconciliation or explicit review. A local spawn/receipt crash window may also remain `UNKNOWN` until the host proves whether the process started; absence of a heartbeat or elapsed time alone proves nothing. A process or client disconnect MUST NOT be interpreted as task completion, process death, cancellation, or permission to relaunch. A new execution MAY continue the same Attempt only for the same bounded strategy after the old writer/effects are settled; execution count and resource use have finite limits that survive restart. A changed strategy or implementation retry MUST create a new Attempt. An execution exit receipt MUST NOT mark its Attempt successful or Task passed; completion still requires current independent evidence (`ARCH/23`, `ARCH/25`).
- `REQ-HORIZON-029` — `CMP-orch` MUST serialize system-wide long-horizon Run admission, model-driven worker/direct-turn execution admission, and application-maintenance acquisition through one durable `SupervisorControlStream` and a cross-process admission lock. A run start or work execution is not acknowledged as admitted until its control event and canonical Run/Thread record are reconciled; update maintenance MUST atomically prevent new run/work admission before executable replacement. After a crash, unresolved admission/maintenance intents MUST be reconciled against per-Run/Thread streams, active processes, effects, and binary digests before reopening admission. A rebuildable SQLite projection MUST NOT be the authority for either decision; stale or unknown state fails closed (`ARCH/16`, `ARCH/25`, `ARCH/30`).
- `REQ-HORIZON-030` — The TUI, CLI/headless surfaces, and protocol adapters MUST use one versioned `CMP-control-api` dispatcher and one set of canonical domain owners; an app-server/client transport MUST NOT create duplicate Run, Thread, permission, or update state. In-process and same-host IPC calls MUST have equivalent typed semantics, mutation idempotency, authorization scopes, bounded request/event lanes, and per-aggregate snapshot/cursor replay with explicit gap handling. Detached execution MUST use a supervised same-binary process, OS-authenticated local endpoint, and recovery-before-mutation gate. Remote listeners are out of scope until a separate authenticated/encrypted remote protocol is approved and accepted. On unsupported platforms, the system MUST report detach as unavailable rather than claim supervision (`ARCH/31`, `DEC-063`).
- `REQ-HORIZON-031` — In an explicitly enabled managed Run, authorized operator and worker principals MAY exchange bounded text messages only with explicit Run-member Thread recipients through the controller-owned mailbox. The Run stream MUST be canonical for posted content and delivery transitions; recipient Thread inbox admission MUST use stable idempotent delivery IDs and reconcile across crashes. Posting, recipient membership, profile capability, guard policy, queue/storage limits, and sender/recipient budgets MUST be checked before acknowledgement. Message content MUST remain untrusted input and MUST NOT change approved intent/specification, permissions, task state, evidence, or completion. Delivery to an active recipient MUST be promoted only at a safe provider-turn boundary; paused, terminal, stale, unknown, or unsupported external recipients MUST NOT be implicitly woken or restarted. Acknowledgement MUST mean only an explicit acknowledgement action, never proof of understanding. The operator UI MUST expose sender, recipient, task, delivery state, failures, queue limits, and replay gaps; muted notification preferences MUST NOT change delivery or execution policy. ACP/CLI adapters MUST report messaging `unsupported` unless a versioned explicit message bridge is negotiated (`ARCH/32`, `DEC-064`).

## REPOSITORY AND DELIVERY

- `REQ-REPO-001` — Repository maps and task context packages MUST retain source revision, file digests, parser/index version, source locations, confidence, and stale-state marker. Source reads and lexical search remain a fallback when semantic indexes are absent or stale.
- `REQ-REPO-002` — Symbol edits and rename operations MUST use versioned source ranges or editor/LSP workspace edits, verify all affected base hashes, and preserve a reviewable diff. A stale semantic result MUST refuse or refresh before writing.
- `REQ-REPO-003` — A managed Run MAY include a bounded set of repositories. Every repository member MUST have an independent canonical root identity, base revision, workspace/fence, integration state, and verification record. Tasks and evidence MUST name the exact member/revision set they touch. Integration is a journaled per-repository saga: a multi-repository result is complete only after every required member passes integration and verification; partial progress is surfaced with explicit per-repo status and recovery/compensation options, never described as an atomic cross-repository commit (`ARCH/25`, `ARCH/23`).
- `REQ-DELIVERY-001` — PR preparation MUST record branch/base/head, intended files, diff review, test and independent review evidence, CI state, and external PR identity. Creating, commenting, merging, releasing, and deploying are separate governed effects with idempotency and approval policy.
- `REQ-RESEARCH-001` — External research used for a design or coding decision MUST record source URL/revision, retrieval time, authoritativeness, relevant excerpt or claim, and whether the claim was independently confirmed. Fetched content remains untrusted data; a stale or unavailable source MUST be labeled, and a model-generated citation MUST NOT be treated as evidence without retrieval.

## PERSONALIZATION AND LOCAL MODELS

- `REQ-PROV-006` — Local inference endpoints MUST be capability-probed per concrete server/model/template combination for tool calls, streaming, cancellation, context limits, structured output, usage, and errors. API compatibility alone MUST NOT enable a feature; unsupported behavior MUST be surfaced and routing must refuse required capabilities it cannot prove.
- `REQ-PROV-007` — Where a model route uses a text edit format instead of structured tool calls, the parser MUST be versioned and conformance-checked for that concrete model/template. Invalid edits may receive bounded diagnostic feedback, but no partial write may be presented as a complete edit; lint/test results are evidence only when their command, exit status, environment, and exact tested revision are recorded.
