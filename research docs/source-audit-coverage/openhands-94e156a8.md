## HLD / feature ownership observed

The repository HLD says Canvas renders/manages UI and frontend state, translates UI actions into Agent Server calls, and packages standalone/library builds. It explicitly does not execute agent actions, provide sandbox/workspace isolation, or run scheduled automation itself ([`docs/architecture.md`](https://github.com/OpenHands/OpenHands/blob/94e156a8c7b7a468d7c60bda3a38757bfbfd4a79/docs/architecture.md)). Its contributor map assigns Agent Server contracts, agents/tools/conversations/events to `software-agent-sdk`; reusable skills, plugins and integrations to `extensions`; and schedules/webhooks/dispatch to `automation`. This is a concrete boundary for HorizonCode: Canvas is integration/UI evidence, not the agent runtime or canonical event/effect model.

## Concrete findings relevant to HorizonCode

### Event transport and UI recovery

- Canvas loads the latest 50 events by REST in descending timestamp order and reverses them for chronological display. Older events are fetched on scroll. The WebSocket asks the server to resend from the last loaded timestamp; on an initial history failure Canvas has a fallback to `resend_mode='all'`. React Query caches history for 30 minutes, refetches on mount, and caps retry at one ([`use-conversation-history.ts`](https://github.com/OpenHands/OpenHands/blob/94e156a8c7b7a468d7c60bda3a38757bfbfd4a79/src/hooks/query/use-conversation-history.ts), [`conversation-websocket-context.tsx`](https://github.com/OpenHands/OpenHands/blob/94e156a8c7b7a468d7c60bda3a38757bfbfd4a79/src/contexts/conversation-websocket-context.tsx#L1025-L1045)). This distinguishes UI catch-up from durable recovery: events come from the server, while the Zustand event projection and optimistic queue are in-memory. The optimistic queue uses a 150-second watchdog and matches the server echo by content/time; it is not an event journal ([`optimistic-user-message-store.ts`](https://github.com/OpenHands/OpenHands/blob/94e156a8c7b7a468d7c60bda3a38757bfbfd4a79/src/stores/optimistic-user-message-store.ts#L1-L18)).
- Local history uses the typed remote-events client. Cloud divides event history (Cloud App API with bearer auth) from live runtime calls such as event count and confirmation response (per-conversation runtime URL and session key). Cloud history pagination is attempted with the filter parameters; on unsupported filters, ordinary UI loading returns an empty page and stops, while completeness-sensitive callers can request strict failure ([`event-service.api.ts`](https://github.com/OpenHands/OpenHands/blob/94e156a8c7b7a468d7c60bda3a38757bfbfd4a79/src/api/event-service/event-service.api.ts#L18-L145), [`event-service.types.ts`](https://github.com/OpenHands/OpenHands/blob/94e156a8c7b7a468d7c60bda3a38757bfbfd4a79/src/api/event-service/event-service.types.ts#L12-L32)). This is a useful adapter pattern, but a partial transcript must remain visibly partial; an empty fallback page cannot be treated as proof that canonical history is exhausted.
- The store deduplicates by event ID, combines transient streaming deltas by sender, and sorts when timestamps arrive out of order ([`use-event-store.ts`](https://github.com/OpenHands/OpenHands/blob/94e156a8c7b7a468d7c60bda3a38757bfbfd4a79/src/stores/use-event-store.ts)). These are display projection mechanics. HorizonCode should keep authoritative append/commit order and gap detection in its event store, then use a replaceable UI projection.

### Tool/agent/request model

- Canvas constructs launch requests from configured settings, with default tool names, optional browser/task tool sets, skills, workspace kind, initial user message, confirmation policy, secrets references, and client tools. It has both an inline-agent path and a profile-ID path; comments acknowledge that profile resolution is server-owned and some inline enrichment must be restored by the Agent Server. Planning launches a raw agent spec. These are frontend request assembly paths, not evidence that agent/tool behavior is implemented or enforced in Canvas (`src/api/agent-server-adapter.ts`, partial read; focused tests in `src/api/agent-server-adapter.test.ts`, partial read).
- For a local runtime, the adapter selects `LocalWorkspace`; when server info says Docker execution it selects `DockerExecutionWorkspace`. Confirmation settings are sent as `NeverConfirm`, `AlwaysConfirm`, or `ConfirmRisky` policy plus an optional analyzer. These request fields express configured behavior; they do not establish OS confinement. The HLD warns that full host access is possible in local mode and recommends Docker sandboxing for laptop use ([`docs/architecture.md`](https://github.com/OpenHands/OpenHands/blob/94e156a8c7b7a468d7c60bda3a38757bfbfd4a79/docs/architecture.md#L45-L83)). Do not translate confirmation mode or a tool annotation into a HorizonCode reach guarantee.
- Canvas registers a UI-control client tool for switching visible panels and a child-conversation launcher. The latter explicitly performs stateful, non-idempotent, open-world delegation; its prompt tells the child it has no parent history and requires a self-contained task brief ([`launch-child-conversation-client-tool.ts`](https://github.com/OpenHands/OpenHands/blob/94e156a8c7b7a468d7c60bda3a38757bfbfd4a79/src/api/launch-child-conversation-client-tool.ts)). This supports explicit tool-effect classification and context handoff, but the UI spec annotation is descriptive metadata, not the execution guard.
- A source-level test requires service code to use `@openhands/typescript-client` rather than direct ad-hoc HTTP calls ([`no-direct-agent-server-calls.test.ts`](https://github.com/OpenHands/OpenHands/blob/94e156a8c7b7a468d7c60bda3a38757bfbfd4a79/src/api/no-direct-agent-server-calls.test.ts)). HorizonCode can use the same architectural idea: one typed protocol adapter per boundary, while keeping policy and durable state inside the authoritative runtime.

### Persistence and security boundary

- Backend host, kind, name, and API key are persisted together in browser `localStorage`. Active selection is tab-scoped in `sessionStorage`, with a `localStorage` default for new tabs. Stored entries are structurally validated, but the API key is still readable to same-origin script; that is a browser-storage residual, not a credential vault ([`storage.ts`](https://github.com/OpenHands/OpenHands/blob/94e156a8c7b7a468d7c60bda3a38757bfbfd4a79/src/api/backend-registry/storage.ts#L90-L160)). Conversation metadata stores UI/workspace/profile hints and plugin coordinates, with a comment excluding plugin parameters because they may contain secrets ([`conversation-metadata-store.ts`](https://github.com/OpenHands/OpenHands/blob/94e156a8c7b7a468d7c60bda3a38757bfbfd4a79/src/api/conversation-metadata-store.ts)).
- The local launcher defaults to `127.0.0.1`. A LAN bind strips the session key from injected HTML and flips into API-key-entry/public mode unless explicitly overridden; runtime HTML injection and container flags need separate review because some container modes deliberately allow LAN access ([`bind-host.mjs`](https://github.com/OpenHands/OpenHands/blob/94e156a8c7b7a468d7c60bda3a38757bfbfd4a79/scripts/bind-host.mjs)). This is a useful defense-in-depth pattern, with a named override residual. The server process itself still determines actual sandbox reach.
- Agent Server compatibility is checked by minimum version and endpoint validation. Contributor rules require raising `compatibility.minimumAgentServer` when Canvas starts depending on a new endpoint/field/behavior. HorizonCode should pin negotiated protocol/capability evidence at the runtime boundary rather than infer a guarantee from the UI version alone.

## Proposed add / purge for HorizonCode

These are design transfer recommendations, not upstream code requests:

1. **Add a boundary note for UI catch-up versus runtime recovery.** Document that UI history fetch, socket resend, and optimistic bubbles are presentation/catch-up mechanisms. Keep committed events, run/effect outcomes, gap detection, and recovery authority in the Horizon runtime. Tradeoff: duplicate adapter and integration work, but avoids attributing frontend cache behavior to durable correctness.
2. **Add an explicit partial-history outcome to UI/client integrations.** When pagination is unsupported or incomplete, surface “history may be incomplete” or a typed capability/error state; preserve strict errors for export/acceptance paths. Tradeoff: more visible edge states and version handling, in return for not silently treating fallback exhaustion as complete history.
3. **Add a security note that confirmation policy and client tool hints are not confinement.** Tie any UI choices to the actual OS/container enforcement tier and residual. Tradeoff: more specific UX/security documentation, without making a confirmation toggle look like a sandbox guarantee.
4. **Purge duplicate Canvas product features from the Horizon runtime plan unless a requirement owns them.** Do not copy its backend-selector persistence, React Query cache, chat panels, plugin/skill UX, or client tool UI into core orchestration. Preserve only the protocol adapter and user-visible integration surfaces Horizon actually needs. Tradeoff: less feature parity, smaller canonical state surface, and fewer competing sources of truth.
5. **Do not adopt browser localStorage as Horizon secret persistence.** It is convenient for a single-origin UI and enables reload/new-tab defaults, but exposes keys to same-origin script. Keep broker/OS-backed secret ownership and pass references to runtime components as Horizon requirements specify.

No new HorizonCode architecture edits are made by this audit. These suggestions should be reconciled with current Horizon requirements/decisions before any implementation; they do not authorize changes to user intent or security semantics.
