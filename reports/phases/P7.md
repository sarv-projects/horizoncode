### Leg 7 — slow-consumer overflow: NOT_RUN (harness capability limit, not a product failure)

The outbound queue bound is **source-verified**: `handlers/event.ts:32-38`
`MAX_EVENT_QUEUE_ITEMS = 256`, `MAX_EVENT_QUEUE_BYTES = 2 MiB`,
`MAX_EVENT_QUEUE_NODES = 65_536`, with `offer()` setting
`event stream backlog exceeded; reconnect to resnapshot` instead of buffering.

It could **not** be exercised live offline, for three compounding reasons:

1. **No observation channel.** The chosen signal was `Stream.ensuring(logInfo("event disconnected"))`,
   but `serve.log` contains exactly **one** line (`opencode server listening …`) and
   **0** `event connected` / **0** `event disconnected` entries across all legs —
   Effect INFO logs do not reach this stdout, so the disconnect delta was
   structurally always 0 and cannot distinguish "kept open" from "failed but unlogged".
2. **Client cannot report it.** With the FIFO pre-filled, curl blocks on its first
   write (verified: `frames captured after unblocking: 0`), so it never observes a
   server-side close either.
3. **Kernel buffering absorbs the flood first.** The local create route **ignores
   caller `title` and `metadata`** (responses are 461 bytes with the server's own
   `New session - <timestamp>` title, and no `p7pad`), so every `session.created`
   frame is only ~687 B. 900 events = **618,300 bytes** were absorbed by client
   kernel socket buffering before the server's own queue could fill; the queue
   never reached 256 items.

Reaching it would need either socket buffers below ~128 KiB (sysctl — outside the
repository filesystem boundary) or larger events (which this route will not
accept). Recorded as **NOT_RUN**, not as a pass and not as a product defect.

known zero renders as `provider-reported 0`; a bucket no observation touched still
renders `unknown 0` because there is no evidence.

## Continuation 36 — restore web-search Settings after consent (2026-10-25)

### Root cause / UX ruling

This finding supersedes Continuation 34's overlay-only hypothesis: the toast was present, but the
Settings view was absent because the confirmation had cleared the dialog stack.

The stable focused test showed that a successful consent save is not the cause of the missing frame.
`DialogConfirm.show()` used `dialog.replace()`. Confirm selection then calls `dialog.clear()`, which
empties the complete stack for a replacement dialog. The caller's web-search Settings element was
therefore destroyed before `toggle()`/`revokeConsent()` resumed and saved the accepted choice. The
saved toast was visible, but the Settings route list no longer existed to render its updated state.

The intended flow is source-backed by the existing P7 test journey: after consenting, it continues
to navigate the route list, verifies the newly enabled/unconfigured BYO route, and then revokes its
consent from that same Settings view. §16.7 defines Settings as the user-visible ordered route list
and says enablement joins the route to the cascade; it does not require closing Settings after the
confirmation. Returning to Settings is therefore required for the currently implemented interaction,
not a change to search/provider authority.
