## Direct session and managed work are different lanes

- **Direct coding does not require a Goal or managed Run.** HorizonCode Core owns the direct Session/conversation; Rust owns managed Goal/SpecVersion/Run/Task/Attempt and effect/evidence control ([architecture ownership law](../../arch_V1/README.md#L17-L25), [§17.2–17.3](../../arch_V1/17-GOVERNANCE-DECISIONS.md#L37-L64)). The V1 scope decision explicitly says direct provider sends for non-effect turns do not wait on kernel READY; read-class direct tools may use the validated read fast path. Mutations and opaque/hosted effects still require the common Guard, leases, receipts, and UNKNOWN recovery ([operative plan](../../docs/superpowers/plans/2026-10-11-horizoncode-converged-implementation.md#L811-L835), [DEC-V1-36](../../arch_V1/17-GOVERNANCE-DECISIONS.md#L101-L106)).
- **“No Goal” does not mean “no authority.”** Current Core direct runner code selects a trusted route and requires authenticated permission scope, AgentProfileV2, and ContextSelection pins; it fails if those pins are absent ([`runner/llm.ts`](../../packages/core/src/session/runner/llm.ts#L654-L724)). The latest live-serve E2E failed before producing an accepted assistant response: `direct_provider_authority failed: direct provider pins require the authenticated Core AgentProfileV2 service`; health/session creation and the unauthenticated 401 probe passed, but the write was absent ([HANDOFF](../../HANDOFF.md#L3-L10)). This is **NOT VERIFIED**, not a reason to require a Goal for ordinary direct coding.
- **Managed work remains separately incomplete.** It must follow the Rust-owned accepted-SpecVersion → Run → Task/Attempt → guarded effects → receipts → independent final-revision verification lifecycle. Multi-Task DAG execution is V1 after—not instead of—the accepted single-Task vertical; it stays unavailable until bounded fan-out and aggregate settlement pass ([DEC-V1-31](../../arch_V1/17-GOVERNANCE-DECISIONS.md#L99-L101)).
