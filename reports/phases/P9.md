## 1. Delivered in this phase pass

### Launcher / installer (P9-01)

- `install` now supports `--dry-run`: validates the candidate executable and
  destination paths, prints the canonical `horizoncode` / short `hzcode` plan,
  and writes nothing (no install directory, no shell-profile edit).
- Existing safe-install behavior retained: local `--binary` only, no network
  download, no automatic updater, fail-closed on native Windows/macOS, symlink
  candidate rejection, staged copy + canonical/alias activation with rollback
  snapshots, and `$HOME/.opencode/bin` compatibility.
- Added idempotency and failure-path coverage: repeat install/upgrade, both
  public command names through one entrypoint, dry-run no-write, directory
  destination refusal without replacing the canonical command, and `bash -n`
  syntax validation.
- Nix packaging (`flake.nix`, `nix/opencode.nix`) now installs `horizoncode`
  plus `hzcode` (and a compatibility `opencode` symlink) and uses
  `mainProgram = "horizoncode"`. Added a `horizoncode` flake package alias.
  Nix was **not evaluated** because `nix`/`nix-instantiate` is absent here.

### Clean install / upgrade / rollback matrix (P9-03)

- `scripts/release/clean_install.py` gained `--dry-run` and a validated
  `run_matrix(..., dry_run=True)` plan that checks checkout, candidate/previous
  binaries, migration fixture, state root, and bubblewrap network isolation
  without creating evidence state or executing the installer.
- Migration-fixture validation now reports the precise regular-file/symlink
  failure before containment checks (same fail-closed behavior).
- TUI smoke robustness fixes found by exercising a real built binary:
  - startup window raised from 1.0 s to a bounded 10 s for cold/network-isolated
    launches, with a 1 s drain/settle window after the first frame;
  - bounded 2 s reap wait after SIGKILL before reporting leftover descendants.
- Existing matrix still requires Linux/WSL, a clean separate checkout, pinned
  candidate/previous SHA-256, bubblewrap unshared network, unchanged shell
  profiles, config migration evidence, and manual previous-binary rollback.

### Release audit / gate / notices (P9-03)

- `packages/opencode/script/build.ts` now packages the pinned upstream
  `opencode/LICENSE` and a generated `NOTICE` into every candidate artifact.
  The notice preserves OpenCode MIT attribution and explicitly states that
  HorizonCode's first-party distribution license is unresolved and
  publication/redistribution is not authorized (DEC-V1-11).
- `scripts/release/release_gate.py` now emits a structured `signing_update`
  block that defaults everything unavailable: no trust root, no channels, no
  automatic update, no rollback policy. The existing `UNRESOLVED` string is
  retained for compatibility.
- Release-gate input validation rejects symlinked/non-regular candidate,
  previous, and migration-fixture inputs with precise labels.
- `scripts/release/README.md` documents dry-run paths, artifact LICENSE/NOTICE
  packaging, and the read-only qualification workflow.

### CI qualification (P9-02)

- `.github/workflows/horizoncode-release-qualification.yml`:
  - new `release-tooling` job runs `bash -n install`, the full release-tooling
    unit suite, isolated-build dry run, and clean-install dry run;
  - `linux-candidate` job installs bubblewrap, builds the isolated Linux
    candidate, runs the real local installer/TUI matrix in a network-isolated
    home, then runs the release gate against the isolated clean checkout;
  - remains `workflow_dispatch` only, `contents: read`, no secrets, no
    signing/publishing/upload, and keeps all evidence under
    `kernel/target/horizoncode-release`.
- `.github/workflows/horizoncode-full-validation.yml` now runs installer syntax,
  release-tooling tests, and an isolated-build dry run before the existing
  architecture validators, Guard tests, typecheck, and full gate.

## 52. Continuation — 2026-10-26 (installer path-injection hardening)

### Root-cause trace

`HORIZONCODE_INSTALL_DIR` is selected at `install:104` and then used as a
filesystem destination in quoted path operations. Before this change, the same
value crossed two text-format boundaries without serialization or validation:

- POSIX shell-family profiles received `export PATH=$INSTALL_DIR:$PATH`, and
  fish profiles received `fish_add_path $INSTALL_DIR`; a path containing shell
  syntax was therefore reinterpreted when the profile was sourced.
- In GitHub Actions, the value was written as one newline-delimited
  `GITHUB_PATH` entry. CR/LF could terminate that entry and inject another.

### TDD and minimal correction

- Added pure-function tests first for command-substitution/control syntax
  rejection, whitespace-path formatting for POSIX and fish, and CR/LF rejection.
  RED: all 7 subcases failed with the security-specific message that the
  validator/serializer was absent while raw interpolation remained.
- Added `validate_install_dir` before any destination creation. To avoid relying
  on shell escaping rules for arbitrary syntax, it fails closed unless a
  non-empty value contains only ASCII letters, digits, spaces, `_`, `.`, `/`,
  and `-`; this also rejects every CR/LF and shell metacharacter. The accepted
  safe alphabet is documented in installer help. Ordinary paths containing
  spaces remain accepted.
- Added `format_install_path_command`: POSIX-family output uses a single-quoted
  path before the unexpanded `:$PATH`; fish output passes the single-quoted path
  as one argument. The accepted alphabet contains no quote/backslash characters,
  so that quoting is literal in both forms. `GITHUB_PATH` receives the validated
  path as a single line.
- No installer invocation, file installation, candidate use, CLI spawn, Git/GitHub,
  release gate, dependency operation, Nix, Cargo, signing, publication, or other
  phase file was touched.
