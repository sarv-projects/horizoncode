## Two paths, and they are not the same path

| probe | request | reaches the command registry? |
|---|---|---|
| **A. text** | `POST /session/$SID/message` with the single text part `/name` | **No.** `packages/horizoncode/src/session/prompt.ts` has no slash parser on the prompt path; the leading `/` is parsed client-side (`packages/tui/src/component/prompt/index.tsx`, `packages/horizoncode/src/cli/cmd/run/footer.prompt.tsx`, `packages/horizoncode/src/acp/service.ts`), and the client then calls the command endpoint. |
| **B. dispatch** | `POST /session/$SID/command` `{"command":"name","arguments":""}`  — exactly what the TUI sends | **Yes.** `SessionHttpApi.command` → `SessionPrompt.command` → `Command.get(name)` → template expansion → a real agent turn. |

**Verdict is taken from probe B** — the only path that can execute a command.
Column *text* records probe A: `IGNORED` means the assistant replied conversationally to the
literal string `/name` instead of the command running, which is what a naive `POST /message`
client sees for **every** command however healthy the registry is. `WORKS` therefore means:
HTTP 2xx from the dispatch endpoint, no `Command not found`, and a completed assistant turn
carrying text or at least one tool call.

## Names a TUI cannot type

typed line on whitespace, so what it would actually dispatch is the first token; the table
shows what that token resolves to on the dispatch endpoint.

These rows are **not evidence**: the sweep's server had already exited, so each is a
refused connection rather than an answer. What the registry does show is that the names
exist and contain spaces; a slash-prompt client splits the typed line on whitespace, so
the first token is all it can send, and the command endpoint matches names exactly
— `/Agent Development` cannot reach `Agent Development`.
